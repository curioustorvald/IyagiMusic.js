# 이야기 음악 파일의 한글 인코딩

`.ims`와 `.iss`의 곡 제목, 가사 줄, 크레디트는 **KS C 5601-1992 조합형**이다.
윈도우가 완성형(CP949)을 일반화하기 전까지 한국 DOS 소프트웨어가 쓰던, 비트로
짜맞춘 2바이트 한글 인코딩이다.

## 1. 이름을 정확히 짚기

여기서 혼동하기 쉬운 인코딩이 둘 있고, 이 파일들에 딸린 참고 자료는 그중
틀린 쪽을 가리킨다.

- **KS C 5601-1992 조합형** — 이 파일들이 실제로 쓰는 것.
- **한/글 2바이트 코드**(HNC 코드) — 워드프로세서 자체의 인코딩.

둘은 **한글 음절 영역 전체에서 완전히 같다.** 그래서 한/글 매핑 표로 곡 제목을
풀면 완벽하게 나오고, 그것이 정답처럼 보인다. 갈라지는 곳은 그 위다. 한/글은
옛한글 자모 결합으로 이어지고, 조합형은 그 자리에 기호와 가나와 한자를 둔다.
이야기 가사 줄을 한/글 표로 풀면 스무 글자에 하나꼴로, 괘선 문자나 가나가
있어야 할 자리에 옛한글 덩어리가 나온다. *(측정: 코퍼스 텍스트의 2바이트 코드
276 196개 가운데 한글 음절 238 775개, 가나 15 172개, 그 밖의 기호 8 495개,
한자 792개, 낱자모 338개.)*

조합형을 쓸 것.

## 2. 바이트 구조

0x80 미만의 바이트는 ASCII이며 홀로 선다. 0x84 이상의 바이트는 2바이트 코드의
시작이고, 상위 바이트가 먼저 온다.

| 첫 바이트 | 내용 |
|-----------|------|
| `0x84`–`0xD3` | 한글 음절과 낱자모 — §3 |
| `0xD4`–`0xD8` | **미할당** — 이야기의 사용자 정의 글자가 여기 있다, §5 |
| `0xD9`–`0xDE` | 기호, 문장부호, 가나, 키릴, 괘선 — §4 |
| `0xDF`        | 미할당 |
| `0xE0`–`0xF9` | 한자 — §4 |
| `0xFA`–`0xFF` | 미할당 |

## 3. 한글 영역

16비트 코드는 네 개의 비트 필드다.

```
 15  14        10  9         5  4         0
+---+------------+------------+------------+
| 1 |  초성 (5)  |  중성 (5)  |  종성 (5)  |
+---+------------+------------+------------+
```

각 필드는 자리 번호이고, 그 번호는 **연속되지 않는다.** 중성과 종성 표에 있는
빈칸이 바로 자모의 자연스러운 묶음과 비트 배치를 맞춰 주는 장치다.

**초성, 자리 2–20**, 순서대로:

```
ㄱ ㄲ ㄴ ㄷ ㄸ ㄹ ㅁ ㅂ ㅃ ㅅ ㅆ ㅇ ㅈ ㅉ ㅊ ㅋ ㅌ ㅍ ㅎ
```

자리 1은 *채움* 코드(초성 없음)다.

**중성, 자리 3–7, 10–15, 18–23, 26–29**, 순서대로:

```
ㅏ ㅐ ㅑ ㅒ ㅓ | ㅔ ㅕ ㅖ ㅗ ㅘ ㅙ | ㅚ ㅛ ㅜ ㅝ ㅞ ㅟ | ㅠ ㅡ ㅢ ㅣ
```

자리 2가 채움 코드다. 자리 0, 1, 8, 9, 16, 17, 24, 25, 30, 31은 쓰이지 않는다.

**종성, 자리 1 = 없음, 자리 2–17과 19–29**, 순서대로:

```
ㄱ ㄲ ㄳ ㄴ ㄵ ㄶ ㄷ ㄹ ㄺ ㄻ ㄼ ㄽ ㄾ ㄿ ㅀ ㅁ | ㅂ ㅄ ㅅ ㅆ ㅇ ㅈ ㅊ ㅋ ㅌ ㅍ ㅎ
```

자리 18은 쓰이지 않고, 자리 0은 나타나지 않는다.

세 필드가 모두 할당된 값이면 유니코드 음절은 통상의 조합 공식으로 얻는다.

```
U+AC00 + 초성첨자 × 588 + 중성첨자 × 28 + 종성첨자
```

첨자는 위 목록에서 0부터 세고, 종성이 없으면 종성첨자는 0이다.

*(측정: 이 분해로 현대 한글 음절 11 172개가 모두 정확히 복원되며, 세 필드 어느
쪽에도 뜻이 겹치는 자리가 없다.)*

**채움 코드**는 낱자모, 곧 U+3131 이후의 호환 자모를 만든다.

- 초성 + 중성채움 + 종성없음 → 초성 낱자, 예: `0x8841` = `ㄱ`
- 초성채움 + 중성 + 종성없음 → 중성 낱자
- 초성채움 + 중성채움 + 종성 → 종성 낱자, 예: `0x8444` = `ㄳ`
- 셋 다 채움(`0x8441`) → U+3000, 전각 공백

한글 첫 바이트 범위이면서 필드가 해석되지 않는 코드는 그냥 미정의다.

## 4. 기호와 한자 영역

여기는 산술이 아니라 표가 필요하다. 두 첫 바이트 범위가 하나의 조밀한 첨자로
합쳐진다.

```
leadIndex  = lead - 0xD9              0xD9–0xDE일 때
           = lead - 0xE0 + 6          0xE0–0xF9일 때
trailIndex = trail - 0x31             0x31–0x7E일 때
           = trail - 0x43             0x91–0xFE일 때
index      = leadIndex × 188 + trailIndex
```

첫 바이트 32개 × 둘째 바이트 188개 = 6016칸이고 그중 5825칸이 할당돼 있다.
내용은 KS X 1001의 한글 아닌 절반, 곧 문장부호, 전각 라틴/그리스 문자, 괘선,
히라가나와 가타카나, 키릴 문자, 그리고 한자 4888자다.

이 저장소의 `tools/gen_johab_table.py`가 그 표를 다시 만들어 준다.

## 5. 이야기의 사용자 정의 글자

첫 바이트가 `0xD4`–`0xD8`인 코드는 조합형에서 미할당이고, 이야기는 `0xD4xx`를
자기 글꼴의 글자에 쓴다. ISS 타이틀 화면을 꾸미는 장식 문자들이다. 한 줄을
좌우 대칭으로 감싸거나, 이름의 글자 사이에 구분자처럼 끼어 나타난다.

*(측정: 서로 다른 코드 84개가 12 624번 나타나며, 그중 60개가 `0xD4` 아래에
있다. 코퍼스 텍스트 전체 2바이트 코드의 4.6%다.)*

이 글자들에는 대응이 없다. 글꼴 안에만 존재하기 때문이다. 디코더는 짐작하지
말고 호출자에게 넘겨야 한다. `decodeJohab()`이 받는 `userGlyph` 콜백이 바로
그 용도다. 글꼴을 가진(또는 글자마다 그럴듯한 유니코드 대체를 가진) 플레이어는
그것을 주면 되고, 나머지는 U+FFFD가 된다.

이 영역 바깥에도 풀리지 않는 코드가 24개, 모두 84번 나타난다. 한글 범위의
할당되지 않은 자모 조합, 할당되지 않은 KS X 1001 칸, 그리고 둘째 바이트가
구조적 빈틈인 0x7F–0x90에 든 것 다섯 개다. 두 번째 글자 영역이 아니라 개별
파일의 인코딩 실수다. 곡 제목 두 개가 멀쩡한 일본어 텍스트 한가운데에 하나씩
달고 있다.

## 6. 글자 칸

이 파일들이 겨냥한 텍스트 화면에서 **1바이트 코드는 한 칸, 2바이트 코드는 두
칸**을 차지한다. 규칙은 이것이 전부이며, ISS의 강조 레코드가 세는 단위가 바로
그 칸이다(FILE_FORMATS §4.2).

디코딩은 그 정보를 버린다. 유니코드 문자열은 어떤 문자가 몇 바이트로 들어왔는지
더 이상 기억하지 못한다. 그래도 코드 포인트만으로 되찾을 수 있다. 두 바이트 길이가
서로 겹치지 않는 범위로 떨어지기 때문이다.

```
두 칸  ⟺  코드 포인트 >= U+0080
```

이는 어림짐작이 아니라 정확하다. 2바이트 코드 중 U+0080 미만으로 풀리는 것은
하나도 없고, 1바이트 코드는 정의상 모두 ASCII다. 2바이트 코드 65 536개와
1바이트 코드 128개 전부에 대해 확인했다.

솔깃한 대안은 유니코드의 East Asian Width 속성인데, 그것은 다른 질문이고 다른
답을 준다. 현대 글꼴이 문자를 어떻게 배치하는지를 기술할 뿐, DOS 화면이 몇 칸을
주었는지가 아니다. 할당된 2바이트 코드 17 065개 중 **470개**에서 어긋난다.
거의 전부가 두 무리다.

- U+2E80 아래에 있는 KS X 1001 기호 행들. `·` `‥` `…` `―` `※` `☆` `★` `○`
  `■` `◁` `▶` `▒` `♥` `♪` `→`, 괘선 문자 전체, 원문자와 괄호문자, 수학 기호.
- 그리스 문자와 키릴 문자. 유니코드는 이들을 East Asian *Ambiguous*로 분류한다.
  서구 문맥에서는 좁지만, 실제로 이들을 그렸던 화면에서는 두 칸이었다.

디코더가 스스로 만들어 넣는 문자는 자기가 빌려 온 문자의 폭이 아니라 **자기가
대신하는 코드의 폭**을 물려받는다. 여기의 디코더가 만들어 내는 두 문자, 곧 §5의
글꼴 글자를 위해 `userGlyph` 콜백이 돌려주는 대체 문자와 그것이 없을 때 쓰는
U+FFFD는 둘 다 2바이트 코드를 대신하므로 글꼴이 어떻게 그리든 두 칸을 차지한다.
`IyagiMusic`의 기본 대체 문자는 가운뎃점 U+00B7이다. 좁아 보이는 문자 하나가
두 칸이다.

*(측정: 코퍼스 `.iss` 696개에서 이 방식으로 센 칸 수는 41 849개 화면 줄 전부에서
파일 자신의 바이트 계산과 일치한다. 대신 East Asian Width로 세면 567개 파일의
6144줄에서 어긋났고, 그 때문에 강조 레코드 19 216개가 엉뚱한 글자를 가리켰다.)*

## 7. 구현

- `src/johab2unicode.js` — ES 모듈, 의존성 없음
- `tools/johab2unicode.py` — Python 3, 의존성 없음, CLI로도 쓸 수 있음

둘 다 CPython에 내장된 `johab` 코덱과 2바이트 코드 32 768개 전부에 대해
비교하고, 서로 간에도 비교하여 `test/test_johab.py`가 검증한다. 그 코덱과
의도적으로 다른 곳은 사용자 정의 영역 하나뿐이다. 코덱은 이 영역을 거부하지만
여기의 디코더는 `userGlyph` 훅으로 넘긴다.

필드 텍스트는 고정 길이에 NUL로 채워져 있다. `decodeJohabField` /
`decode_johab_field`가 뒤쪽의 NUL과 공백을 먼저 떼어 낸다. 필드 안의 NUL은
거기서 문자열이 끝났다는 뜻이다. 다만 BNK 음색 이름과 일부 ROL 음색 이름은
종료자 뒤에 NUL이 아닌 쓰레기 값을 달고 있으므로, 중간의 NUL을 걸러 내지 말고
첫 NUL에서 자를 것.
